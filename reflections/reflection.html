Structured Reflections

Reflection component of all 5 artefacts (50 marks)

Each reflection follows a structured pattern: what the artefact is, what I learned while producing it, and how it demonstrates development.

1. Agile Team Charter — Reflection

Writing the charter forced me to make implicit assumptions explicit. Before this, I treated "definition of done" as something obvious; writing it down showed that ambiguity in small agreements causes avoidable rework. I learned that a charter is only useful if it is referenced — so I linked it to the Trello board description and used it to justify prioritisation in the product backlog.

2. User Stories & Tasks — Reflection

Converting features into user stories changed how I thought about the app. Features I had described technically ("live tracking page") became needs ("decide whether to wait for a bus"). Breaking stories into tasks exposed hidden work — for example, empty and error states, which are easy to forget until a user hits them. This artefact demonstrated development in my ability to think from the user's perspective.

3. Product Backlog — Reflection

Prioritising the backlog made the biggest project risk obvious: the backend API is still under development, so many frontend features depend on a component that does not yet exist. I learned to separate "feature complete" from "system complete". The backlog also gave me a vocabulary for deferring low-value work (accessibility pass) without guilt, because the trade-off is now visible in a table rather than in my head.

4. Sprint Backlog — Reflection

The sprint backlog demonstrated the value of a narrow goal. Committing to four tasks rather than the entire backlog made progress measurable and honest. I learned that the sprint goal should be a sentence, not a list — if I cannot state the goal in one sentence, the sprint is probably too broad.

5. Agile Logbook — Reflection

The logbook was the artefact that changed my behaviour the most. Recording daily stand-ups created a paper trail I could not rationalise away, and the retrospective surfaced a concrete improvement (add a test-data task to every sprint). I learned that reflection is most valuable when it produces an action, not just an observation.

Overall Reflection

Across the five artefacts, my development is visible in three ways: I moved from technical descriptions to user-centred ones, from implicit agreements to written ones, and from ad-hoc work to a visible board. The portfolio is not a record of perfect process — it is a record of a process that improved because it was written down.
